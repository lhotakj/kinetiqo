# Kinetiqo AI Chat — Implementation Specification

> **Status:** Ready for implementation  
> **Scope:** First production-ready release of an authenticated, persistent, multimodal AI chat integrated into Kinetiqo.  
> **Primary provider:** Google Gemini.  
> **Architecture:** Provider-neutral core; only Gemini must be implemented in the first release.  
> **Database support:** PostgreSQL, MySQL/MariaDB, and Firebird.  
> **Required project instructions:** Read and follow `AGENTS.md`, `SKILLS.md`, `README.md`, `docs/MCP.md`, `docs/DATABASE.md`, and the relevant existing web, settings, authentication, database, and MCP implementation before changing code. The source code and tests are authoritative when documentation differs.

---

## 1. Purpose and product outcome

Add an AI Chat page to Kinetiqo so an authenticated athlete can ask natural-language questions about their training and receive useful, data-grounded answers without configuring a separate AI client.

The feature must reuse Kinetiqo's existing data, analytics, authentication, and MCP tool layer. It must not independently query Strava or duplicate analytics calculations in the chat code.

Example questions:
- “Summarize my training over the last four weeks.”
- “Compare this month with the same month last year.”
- “What are my current fitness, fatigue, and form values?”
- “Which rides contributed most to my recent training load?”
- “Explain this activity chart.” (with an uploaded image)
- “Review this training-plan PDF.” (where the selected provider/model supports PDF input)

### 1.1 User-visible outcomes

A user can:
1. Configure and validate an AI provider API key in Settings.
2. Open `/chat`, start a conversation, select an available model, and send text.
3. See the answer stream incrementally, with clear loading, cancellation, error, and retry states.
4. Return later and see conversation history.
5. Create, rename, and delete conversations.
6. Attach supported images and PDFs, see attachment previews, and download attachments generated by the model.
7. Ask questions about their Kinetiqo training data through a tightly controlled, read-only tool interface.
8. See which provider/model answered and, when available, input/output token usage.
9. Understand that prompts, selected data, and attachments are sent to the configured external AI provider.
10. Use the feature with any supported Kinetiqo database backend without database-specific behavior leaking into the service layer.

### 1.2 Product principles

- **Athlete privacy:** every session, message, key, upload, and generated artifact is scoped to the authenticated athlete.
- **Data provenance:** answers about Kinetiqo data should be grounded in tool results, distinguish facts from interpretation, and not invent metrics.
- **Read-only tools:** chat tool calling must not trigger syncs, edit athlete settings, or write to Strava.
- **Provider isolation:** provider-specific request/response formats stay inside provider adapters.
- **No hidden data transfer:** show a clear disclosure before the first external-provider request and when configuring a provider.
- **Progressive enhancement:** text-only chat works without attachment support; the app remains usable on desktop and mobile.
- **No network in tests:** unit tests mock provider APIs, MCP execution, and database boundaries.
- **Fit existing Kinetiqo:** use current authentication, CSRF, templates, Tailwind build, local vendor library process, repository abstraction, logging, and design conventions.

## 2. Scope and explicit non-goals

### 2.1 Included in first release

- Provider-neutral chat domain model and adapter interface.
- Gemini provider: key validation, model discovery, text streaming, supported image/PDF inputs, provider errors, and usage metadata where available.
- Encrypted per-athlete provider keys.
- Persistent conversations and messages.
- `/chat` UI, conversation list, model selector, markdown responses, streaming, retry, stop/cancel, and keyboard accessibility.
- Upload and download of supported attachments, with server-side validation and safe storage.
- Read-only Kinetiqo data tools through the existing MCP/tool service layer.
- Database implementation for PostgreSQL, MySQL/MariaDB, and Firebird.
- Unit tests, route tests, security tests, documentation, and deployment/configuration notes.

### 2.2 Not included in first release

- OpenAI, Anthropic, or Mistral provider implementations. The abstraction must make these addable without changing the chat service or persistence contract.
- Voice input/output.
- Shared or collaborative conversations.
- Public chat links.
- Autonomous background agents or scheduled AI actions.
- Any chat-triggered Strava writes, profile writes, or synchronization.
- Vector databases, embeddings, or a separate RAG index.
- AI-generated images unless the chosen Gemini model and API response format explicitly support it and the implementation can safely persist and serve them. Text-only answers must not depend on image generation.
- Automatic conversation summarization unless it is implemented as an explicit, testable context-management feature. Never silently remove old history from the visible conversation.

## 4. High-level architecture

Keep responsibilities separate:

```text
Browser
  ├── /chat and /chat/<session_id> (Jinja page)
  ├── static/js/chat.js + chat styles
  └── authenticated JSON / SSE endpoints
          |
          v
Flask routes (authentication, CSRF, request validation, response mapping)
          |
          v
ChatService
  ├── ConversationService / persistence operations
  ├── ProviderKeyService + encryption
  ├── AttachmentService + safe local storage
  ├── ContextBuilder + read-only ToolExecutor
  └── ProviderRegistry
          |
          +--> ChatRepository contract
          |       +--> PostgreSQL
          |       +--> MySQL/MariaDB
          |       +--> Firebird
          |
          +--> ChatProvider interface
                  +--> GeminiChatProvider (first release)
                  +--> future provider adapters
          |
          +--> existing Kinetiqo MCP/data-tool service
                  (read-only allowlist only)
```

### 4.1 Suggested package structure

Adapt to the actual project conventions, but keep these responsibilities distinct:

```text
src/kinetiqo/chat/
  __init__.py
  models.py                 # domain dataclasses/enums
  service.py                # orchestration and conversation rules
  repository.py             # chat persistence interface if not part of DB repository
  encryption.py             # authenticated encryption for provider keys
  attachments.py            # validation, storage, ownership checks
  context.py                # system instructions and context assembly
  tools.py                  # allowlisted read-only Kinetiqo tool execution
  errors.py                 # normalized application/provider errors
  providers/
    __init__.py              # explicit provider registry
    base.py                  # provider protocol and shared types
    gemini.py                # Gemini implementation
src/kinetiqo/web/
  templates/chat.html
  static/js/chat.js
  static/css/chat.css
tests/
  test_chat_*.py
```

The implementation may choose a different layout if the repository already has a clearer established pattern. Do not create duplicate abstractions for the same responsibility.

### 4.2 Core request lifecycle

1. Browser sends an authenticated, CSRF-protected request.
2. Route validates shape, size, content type, and request limits.
3. Route resolves the session using `current_user.id`; failure to find a session owned by the user returns 404.
4. Service obtains the configured provider key from the database or documented environment override.
5. Service validates provider/model availability and attachment ownership/compatibility.
6. Service loads persisted history and constructs a bounded provider request. The system instruction is generated by the server, never supplied by the browser.
7. If tools are enabled, the model may request only allowlisted read-only tools. The server validates and executes each call, then sends structured tool results back to the provider.
8. Provider text deltas are sent as application-defined SSE events.
9. On successful completion, the final assistant message, attachment metadata, provider/model, and token usage are persisted.
10. On failure or cancellation, the user message remains recoverable and the assistant turn is marked as failed/interrupted; partial output must not be presented as a complete answer.
11. Every exit path closes the upstream stream and releases resources.

Do not hold a database transaction open while waiting for a model response.

## 5. Domain model and persistence contract

Use explicit domain types and validation. Database rows must not be passed directly into provider adapters or templates.

### 5.1 Conversation/session

A conversation represents a durable thread.

Required fields:
- `session_id`: opaque UUID string generated server-side.
- `athlete_id`: authenticated owner.
- `title`: non-null bounded string; initially a safe placeholder such as “New chat”.
- `provider`: provider key, e.g. `gemini`.
- `model_id`: selected model identifier.
- `created_at`, `updated_at`: UTC timestamps.
- Optional `last_message_at` if useful for ordering; avoid redundant fields unless needed.

Rules:
- Default list order: most recently updated first.
- Creating a conversation must not call an external provider.
- A session’s provider/model can be changed for a new turn if the selected model is configured; record provider/model per message so historical turns remain interpretable.
- Rename is an explicit operation. Auto-title is derived only from the first user message unless model-generated titling is deliberately added later.
- Titles must be length-limited and rendered as text, never HTML.
- Deleting a session deletes all its messages and owned attachment references, and attempts provider-side cleanup of remote file uploads where supported. Remote cleanup failure must not prevent local deletion.

### 5.2 Messages

Each message must include:
- `message_id`: backend-compatible generated identifier or UUID.
- `session_id`, `athlete_id`.
- `role`: `user` or `assistant` for persisted visible messages. Tool calls/results should be represented in structured internal message parts or metadata, not confused with visible assistant prose.
- `content`: plain text / Markdown source; never pre-rendered HTML.
- `attachments`: nullable JSON text describing attachments, never raw file bytes.
- `provider`, `model_id`: nullable for user messages if not meaningful; set for assistant responses.
- `status`: at minimum `complete`, `failed`, `interrupted` (or an equivalent explicit field).
- `input_tokens`, `output_tokens`: nullable integers if the provider reports them.
- `created_at`.

Persist user messages before making the provider request so a browser disconnect does not lose the prompt. Persist assistant output only according to the completion policy. If partial output is saved, it must be marked `interrupted` and be clearly labeled in the UI.

Message history must be loaded in deterministic chronological order. Use stable ordering such as timestamp plus message ID, or an increasing per-session sequence if the existing DB conventions support it.

### 5.3 Attachments

Persist only metadata in message JSON; keep bytes in the configured local artifact/upload store using opaque server-generated IDs.

Attachment descriptor fields:
- `attachment_id`
- `owner_athlete_id`
- `session_id` and/or `message_id` when associated
- `original_filename` (display-only, sanitized)
- `mime_type` (detected server-side)
- `size_bytes`
- `sha256` (integrity/deduplication aid, not authorization)
- `storage_kind` (`local` or provider-managed reference)
- `storage_key` (opaque, server-generated key)
- `provider_file_id` / `provider_file_uri` only when needed
- `provider_file_expires_at` when applicable
- `created_at`
- optional `deleted_at`

Do not store user-controlled filesystem paths. Resolve attachment IDs to metadata in the database and then to a server-controlled storage location. Enforce ownership on upload association, viewing, download, deletion, and provider submission.

### 5.4 Provider keys

One key per athlete and provider:
- `key_id`
- `athlete_id`
- `provider`
- `api_key_enc`
- `is_valid`
- `validated_at`
- `created_at`, `updated_at`

Add a unique constraint/index on `(athlete_id, provider)`. The database must never store provider API keys in plaintext. Do not return ciphertext or plaintext to the browser. The UI may show only a configured/unconfigured state and a masked suffix if the project’s security policy explicitly permits it; safest default is not to display any key characters.

### 5.5 Database portability

Implement schema entries and repository methods for all supported backends. Verify exact type and index syntax against current `schema.py` conventions.

Important portability points:
- PostgreSQL identity columns and timezone-aware timestamps must match existing conventions.
- MySQL/MariaDB auto-increment and index-length rules must be respected.
- Firebird identity support, identifier quoting, descending-index syntax, large text fields, booleans, and timestamp behavior must match the versions supported by Kinetiqo.
- Large message bodies and JSON descriptors must use suitable large-text/BLOB types; do not use a short Firebird `VARCHAR` for potentially large JSON.
- Do not assume `ON DELETE CASCADE` is available/consistent unless the project’s schema mechanism and all three backends support it. Explicit transactional deletion is acceptable.
- All queries must be parameterized. Table/column names must come from static code, never request input.
- All writes that span multiple rows must be transactional.
- Every query involving user data must constrain by owner (`athlete_id`) and relevant session/attachment ID.

### 5.6 Repository methods

Add the minimum coherent contract needed by the service, with naming adapted to the existing repository style:

- Create/list/get/update/delete sessions.
- Get session by ID and owner.
- Insert user message.
- Insert/update assistant message status and final content.
- List messages for owned session with pagination or a bounded history limit.
- Get/delete attachment metadata; associate attachment with a message/session.
- Get/upsert/delete provider key by athlete/provider.
- Mark key validity and validation timestamp.
- Cleanup orphaned attachment metadata where appropriate.

Repository functions must return normalized domain records, not driver-specific row types. Add tests for every backend implementation using the project’s mocking/testing conventions.

## 6. Provider-neutral contract

The core must not know Gemini request JSON, SSE payloads, or SDK types.

### 6.1 Shared types

Define provider-neutral types similar to:

```python
from dataclasses import dataclass, field
from typing import AsyncIterator, Literal, Protocol

Role = Literal["system", "user", "assistant", "tool"]

@dataclass(frozen=True)
class ChatAttachment:
    attachment_id: str
    mime_type: str
    filename: str
    size_bytes: int
    # Provider adapters receive validated content/reference objects,
    # never a client-supplied path or arbitrary URI.

@dataclass(frozen=True)
class ChatMessage:
    role: Role
    content: str
    attachments: tuple[ChatAttachment, ...] = ()

@dataclass(frozen=True)
class ChatProviderModel:
    id: str
    display_name: str
    input_token_limit: int | None = None
    output_token_limit: int | None = None
    supports_vision: bool = False
    supported_mime_types: tuple[str, ...] = ()
    supports_tools: bool = False

@dataclass(frozen=True)
class Usage:
    input_tokens: int | None = None
    output_tokens: int | None = None

@dataclass(frozen=True)
class StreamEvent:
    # Prefer typed events rather than magic strings mixed with text.
    type: Literal["text_delta", "tool_call", "usage", "completed"]
    text: str | None = None
    tool_call: object | None = None
    usage: Usage | None = None

class ChatProvider(Protocol):
    async def validate_key(self) -> None: ...
    async def list_models(self) -> list[ChatProviderModel]: ...
    def stream(
        self,
        *,
        model_id: str,
        system_instruction: str,
        history: list[ChatMessage],
        new_message: ChatMessage,
        tools: list[dict] | None = None,
        max_output_tokens: int | None = None,
    ) -> AsyncIterator[StreamEvent]: ...
```

This is an illustrative contract, not a requirement to copy it verbatim. Choose one consistent interface and test it. In particular:
- Do not encode usage metadata in strings such as `__usage__:100:30`.
- Do not mix model output, errors, tool calls, and usage in a single untyped text stream.
- Do not expose SDK response objects outside the adapter.
- Provider-specific capabilities must be explicit; unsupported attachment types should fail before an API request with a clear message.

### 6.2 Provider registry

Use an explicit static registry, not dynamic imports from user input:

```python
PROVIDER_REGISTRY = {
    "gemini": GeminiChatProvider,
}
```

The provider key comes from validated server-side configuration/database records. Unknown providers return a controlled unsupported-provider error. Do not advertise unimplemented OpenAI/Anthropic/Mistral providers in the UI.

### 6.3 Error taxonomy

Normalize provider failures into application errors:
- `ChatConfigurationError` — no key, invalid model, unsupported capability.
- `ChatAuthenticationError` — provider rejected key.
- `ChatRateLimitError` — throttled/quota exhausted.
- `ChatTimeoutError` — timeout.
- `ChatProviderUnavailableError` — upstream unavailable.
- `ChatProviderResponseError` — malformed or unexpected response.
- `ChatContextLimitError` — request exceeds context/input limits.
- `ChatAttachmentError` — invalid, expired, unsupported, or inaccessible attachment.
- `ChatCancelledError` — user stopped generation or client disconnected.

Return safe, actionable messages to the browser. Log technical details without secrets, raw attachment contents, or full prompts. Never return provider stack traces or raw upstream error bodies.

## 7. Gemini provider implementation

Use the official Gemini API through the project-approved client library or `httpx`, after verifying current API support and dependency compatibility. Prefer one approach for streaming and test it thoroughly; do not keep two production paths “just in case”.

### 7.1 Authentication and key validation

- Send the key in the provider’s supported authentication header, never in a URL/query string.
- Use a bounded connection/read timeout.
- Validate the key on save by making a lightweight authenticated request that confirms access. Distinguish invalid credentials from quota/network/server errors; do not mark a key invalid for a transient timeout.
- Never log the key, headers, full request body, or URL containing credentials.
- If validation fails, do not replace a previously working key unless the user explicitly confirms replacement or the route’s behavior is clearly documented.
- Return a generic validation result to the browser; no secret material is returned.

### 7.2 Model discovery

- Fetch available models from the authenticated provider endpoint.
- Filter by supported text-generation capability and any required capabilities.
- Normalize IDs by removing provider resource prefixes only if the actual chat endpoint expects the shortened identifier.
- Use provider-supplied model metadata when available; unknown metadata must be `None`/unknown rather than guessed.
- Handle pagination.
- Cache model results server-side with a TTL and invalidate when a key is changed or removed. A browser cache may be added for UX, but it must not be the source of truth or keyed by a truncated API-key hash.
- Do not assume model names, context sizes, output limits, or file-expiration periods are permanent. Treat them as provider metadata/configuration and verify the current API contract at implementation time.
- Return only models that are actually supported by the configured key and API endpoint.

### 7.3 Streaming protocol

- Parse the provider’s actual streaming protocol robustly, including partial network chunks and multi-line SSE events where applicable.
- Extract only supported text parts into `text_delta` events.
- Extract usage metadata if supplied.
- Detect finish reason, blocked/safety responses, malformed events, and upstream errors.
- Ignore empty/non-text parts safely; do not stringify arbitrary objects into the response.
- Always close response streams/clients in `finally`.
- Apply timeouts and handle cancellation/disconnection.
- Do not retry a stream automatically after any output has been emitted, because this can duplicate or alter the answer. Retry only when the request is known not to have started, and only with bounded attempts.

### 7.4 Multimodal requests

Build provider payloads from validated attachment descriptors and bytes resolved server-side.

- Supported first-release uploads: JPEG, PNG, WebP, and PDF, subject to actual provider/model support.
- GIF may be accepted only if it is intentionally supported and safely normalized; otherwise reject it. Do not claim a capability that is not tested.
- Validate actual file signatures/MIME, not only filename or browser-supplied MIME.
- Enforce limits before buffering or base64 encoding.
- Use inline content only when within provider and application request-size limits.
- For larger files, use the provider’s file API only if the selected provider supports it; track remote IDs and expiration. Expired remote files must be re-uploaded from local storage if the original file still exists and the user sends it again.
- Do not rely on remote provider file storage as the only copy of a user attachment.
- A file URI must originate from a successful upload by this application; never accept arbitrary user-supplied provider URIs.
- Before sending a request, confirm the selected model supports every attachment MIME type.
- If upload succeeds remotely but local persistence fails, attempt remote cleanup.
- If the provider cannot return image outputs for the chosen model, treat image generation as unsupported rather than silently dropping the response part.

## 8. API key encryption and secret management

### 8.1 Encryption requirements

Use authenticated encryption such as AES-256-GCM from a maintained cryptographic library.

- Generate a fresh cryptographically secure nonce for every encryption operation.
- Derive a dedicated encryption key from the configured secret using HKDF-SHA256 and a fixed application-specific context string.
- Store a versioned envelope, e.g. `v1:<base64(nonce || ciphertext_and_tag)>`, so future key-rotation/envelope changes are possible.
- Validate minimum secret configuration at startup or when AI features are used.
- Never use `SECRET_KEY` directly as an AES key without a KDF.
- Never fall back to plaintext storage if encryption fails.
- Decryption failure must fail closed and produce an actionable operator message, not expose cryptographic details to the user.
- Use constant-time/standard library cryptographic primitives; do not implement cryptography manually.

### 8.2 Secret rotation and configuration

Because deriving the encryption key from Flask `SECRET_KEY` means changing it can make stored keys undecryptable:
- Document that consequence prominently.
- Prefer a dedicated environment setting such as `KINETIQO_CHAT_ENCRYPTION_KEY` if consistent with the existing configuration model. If the project deliberately uses `SECRET_KEY`, specify the exact rotation behavior and test it.
- If supporting old and new key versions, store a key-version identifier and implement an explicit rotation procedure.
- Do not expose encrypted values through settings APIs, HTML, logs, or exception messages.
- Environment-provided provider keys, if supported, must have explicit precedence and UI indication. A database key must not silently override an environment key or vice versa. Follow Kinetiqo’s existing environment-vs-database settings policy and test it.
- Never add a provider key to `.env.example` with a real value.

### 8.3 Key settings UI

The AI settings section must:
- Explain that prompts, relevant Kinetiqo data, and attachments are sent to the selected provider.
- Show provider configured/unconfigured status and last successful validation time.
- Accept a new key via password input with autocomplete disabled where appropriate.
- Never populate the input with an existing key.
- Offer “Validate and save” and “Remove key”.
- Distinguish invalid-key errors from quota/network errors.
- Require CSRF protection and authentication.
- Avoid leaking the key through query strings, analytics, browser storage, flash messages, or logs.
- Warn if a key is supplied by environment configuration and cannot be edited from the UI.

## 9. Kinetiqo MCP/tool integration

The chat must reuse the existing Kinetiqo data/tool layer. Do not implement a second SQL analytics layer for the AI.

### 9.1 First-release behavior

Implement **on-demand read-only tool calling** only if the existing tool layer can be invoked safely in-process with a well-defined contract. If not, ship a deterministic read-only context builder first and leave tool calling behind a feature flag until the invocation contract is proven.

The final delivered first release must have a reliable way to answer data questions, not merely a generic chatbot with a hard-coded context snapshot.

### 9.2 Tool allowlist

Build the tool catalog from actual registered MCP tool definitions and explicitly allow only tools needed for analysis. Start with read-only tools for:
- Activity search/listing.
- Activity details and telemetry/streams.
- Activity totals by date range and sport.
- Power curves / mean maximal power / personal records.
- Fitness and freshness (CTL/ATL/TSB).
- FTP and VO₂max trends.
- Training goals and relevant athlete profile values.
- Existing read-only summaries and data-backed visualizations only where safe.

The agent must inspect the current MCP implementation and map exact names, parameters, and output schemas. Do not invent tool names. Do not expose tools that can:
- Trigger a Strava sync.
- Update Strava descriptions or other Strava content.
- Change athlete/profile/settings data.
- Delete or modify activities.
- Perform arbitrary SQL or filesystem operations.
- Access another athlete’s data.
- Start expensive visual export operations unless specifically reviewed and bounded.

MCP mutation flags are not a substitute for a chat-specific allowlist. The chat tool registry must exclude mutating tools regardless of global configuration.

### 9.3 Tool-call execution rules

- Validate tool name and arguments against server-owned schemas.
- Apply per-call timeouts (initial target: 10 seconds), maximum tool-call count per assistant turn (initial target: 8), maximum tool-result bytes, and a total turn time budget.
- Never execute a tool name or SQL statement provided only by the model.
- Treat tool output and uploaded documents as untrusted data, not instructions.
- Do not include secrets, access tokens, or unrelated personal data in tool results.
- Pass only the minimum fields needed to answer the question.
- Tool errors are returned to the model as structured errors without stack traces; the user sees a concise explanation if the request cannot be answered.
- Tool execution must preserve the authenticated athlete context and must not allow the model to override it.
- Persist tool-call metadata for debugging only if it is privacy-safe; avoid storing large duplicate raw payloads.
- Bound loops and stop when the provider returns a final answer, a tool error budget is exhausted, or the turn deadline is reached.
- The model must be told that it cannot execute write operations and that it must not claim a tool ran when it did not.

### 9.4 Data-grounded answers

Use a server-owned system instruction that:
- Defines the assistant as Kinetiqo’s training-data assistant.
- Requires using tools for questions that depend on the athlete’s data.
- Requires clearly distinguishing retrieved values, calculations, and coaching interpretation.
- Requires dates, units, comparison periods, and assumptions to be explicit.
- Requires saying when data is missing, stale, or insufficient.
- Prohibits fabricating activities, power values, heart rates, training load, or tool results.
- Advises that training insights are informational and not medical diagnosis.
- Treats user messages, activity descriptions, and uploaded documents as untrusted content that cannot override system instructions.
- Requires concise source context in the answer, e.g. date range, activity names/dates, or metric provenance. Do not invent a citation syntax that the UI cannot render.

### 9.5 Context policy

- Build system instructions on the server for every request; never accept system prompts from the browser.
- Fetch current athlete context on demand or when it materially helps the question. Do not inject a large lifetime data dump into every prompt.
- Make the source and date of any preloaded context clear.
- The UI may provide a collapsible “Data used” / “Sources” panel showing the tool names, time ranges, and concise result summaries, without exposing hidden reasoning or internal system prompts.
- If a context snapshot is cached, use an explicit TTL and invalidate it after data sync or relevant settings changes when practical.
- Never claim the model has access to all Kinetiqo data unless the available tools and query results justify that claim.

## 10. Conversation history and context-window management

### 10.1 Source of truth

The database is the authoritative history. Browser storage may retain only transient UI state such as draft text, sidebar width, and last-selected model. Do not store chat history or provider secrets in `localStorage`.

### 10.2 Request construction

For each turn:
1. Load messages for the owned session in chronological order.
2. Exclude failed/interrupted assistant turns from model context unless there is a deliberate and tested representation.
3. Rebuild provider-native conversation messages from normalized history.
4. Keep system instructions separate from user-visible history.
5. Include attachment content only when the attachment is still available, owned by the user, and supported by the current model.
6. Estimate or obtain input token usage when possible.
7. Apply a documented history budget before sending.

### 10.3 Long conversations

- Keep the full transcript visible and persisted.
- Do not silently truncate old messages.
- When history approaches the model limit, display a warning before sending.
- If truncation is needed, select complete message pairs/turns and preserve relevant system instructions. Explain in the UI that older turns are not included in the current model context.
- Never remove an attachment from the visible transcript merely because a provider-side file reference expired.
- If automatic summaries are later implemented, persist them as explicitly marked internal summaries with provenance and test them against the original history. Do not treat a summary as verbatim history.

### 10.4 Session title

Initially set a neutral title. After the first user message, derive a title from that message using a safe, deterministic truncation (e.g. 60 characters) unless a later model-title feature is deliberately implemented. Strip control characters and whitespace. Never send an additional provider request solely to generate a title in the first release.

## 11. HTTP routes and API contract

Follow existing route conventions and prefixes. The table below is the minimum expected API; consolidate or rename endpoints only if that matches established project patterns and all behavior remains covered by tests.

All endpoints require login. All state-changing requests require CSRF protection. Every session/attachment operation must enforce ownership in the database query itself.

| Method | Route | Purpose |
|---|---|---|
| `GET` | `/chat` | Render new-chat page |
| `GET` | `/chat/<session_id>` | Render page and load owned conversation |
| `GET` | `/api/chat/sessions` | List current athlete’s sessions |
| `POST` | `/api/chat/sessions` | Create a session |
| `PATCH` | `/api/chat/<session_id>/title` | Rename owned session |
| `PATCH` | `/api/chat/<session_id>/model` | Set provider/model for future turns, if supported |
| `DELETE` | `/api/chat/<session_id>` | Delete owned session and associated local data |
| `GET` | `/api/chat/<session_id>/messages` | Load bounded history for owned session |
| `POST` | `/api/chat/<session_id>/message` | Start a turn and stream events |
| `POST` | `/api/chat/<session_id>/cancel` | Request cancellation, if the server uses a cancellation registry |
| `POST` | `/api/chat/attachments` | Upload attachment |
| `GET` | `/api/chat/attachments/<attachment_id>` | Serve a preview after ownership check |
| `GET` | `/api/chat/attachments/<attachment_id>/download` | Download after ownership check |
| `DELETE` | `/api/chat/attachments/<attachment_id>` | Delete unattached/owned upload if permitted |
| `GET` | `/api/chat/models` | List models for configured providers |
| `POST` | `/settings/ai-keys/<provider>` | Validate and save key |
| `DELETE` | `/settings/ai-keys/<provider>` | Remove key |

### 11.1 Request validation

- JSON endpoints require `application/json`; upload endpoints require multipart form data.
- Reject malformed JSON, unexpected fields, empty prompts, overlong prompts, invalid session IDs, unknown providers/models, and unsupported attachments with consistent 4xx errors.
- Set explicit limits for prompt length, attachment count, per-file size, total request size, message-history page size, and concurrent generations per athlete.
- Do not accept `athlete_id`, `owner_id`, provider endpoint URLs, arbitrary file paths, or raw provider file URIs from the client.
- Use stable error JSON, e.g. `{ "error": { "code": "rate_limited", "message": "The AI provider is temporarily rate-limiting requests. Please try again shortly." } }`.
- Do not reveal whether another athlete’s session or attachment exists; return 404 for unowned resources.

## 12. SSE streaming contract

Use Server-Sent Events for text generation, consistent with Kinetiqo’s existing progress-streaming patterns. The browser should use `fetch()` with a readable stream when a POST body and CSRF header are required; native `EventSource` cannot send arbitrary POST bodies/headers.

### 12.1 Application events

Use a stable, documented event schema independent of provider protocol:

```text
event: message_start
data: {"message_id":"...","session_id":"..."}

event: text_delta
data: {"message_id":"...","text":"Your "}

event: tool_status
data: {"tool_name":"...","status":"running"}

event: tool_status
data: {"tool_name":"...","status":"completed"}

event: usage
data: {"input_tokens":123,"output_tokens":45}

event: message_complete
data: {"message_id":"...","status":"complete"}

event: error
data: {"code":"rate_limited","message":"The provider is temporarily rate-limiting requests."}
```

The server must send `Content-Type: text/event-stream`, disable proxy buffering where the deployment requires it, and use appropriate cache headers. Send heartbeat comments if needed for long-running requests.

### 12.2 Stream invariants

- Exactly one terminal event (`message_complete` or `error`) per started response where the connection remains open.
- Text chunks are deltas, not complete accumulated content.
- The browser appends text safely and does not re-render the entire transcript on every token.
- Persist the final assistant message and usage before reporting successful completion.
- If the client disconnects, cancel upstream work where possible, close resources, and mark the turn interrupted.
- The server must not rely on a generator-local variable surviving worker restarts.
- Avoid unbounded in-memory buffers. Enforce maximum generated output and total generation duration.
- The UI must handle malformed events, unexpected disconnects, empty streams, and duplicate events without corrupting history.
- Do not automatically retry a partially streamed generation.
- If a request can be retried safely, use a client-generated idempotency/request ID stored server-side to avoid duplicate user messages.

### 12.3 Concurrency

For the first release, allow at most one active generation per conversation and a bounded number per athlete. Return a clear conflict response if a second generation is started in the same session. Do not use an in-memory cancellation registry as if it were cross-worker shared state; if cancellation across multiple Gunicorn workers is required, use a shared mechanism or document the limitation and make the UI behavior accurate.

## 13. Attachments and file safety

### 13.1 Upload limits

Set explicit configurable constants and document them. Suggested initial limits:
- Maximum 5 attachments per message.
- Images: 20 MiB per file.
- PDFs: 25 MiB per file.
- Maximum aggregate attachment size per message: 40 MiB.
- Maximum prompt length: 20,000 characters.
- Maximum model output: bounded by selected model and a server-side cap.

These are application limits, not claims about provider limits. Keep provider limits separate and enforce the stricter applicable limit. Stream uploads to disk or bounded temporary storage rather than reading arbitrarily large files fully into memory.

### 13.2 Validation and storage

- Allow only explicitly supported types.
- Check extension, declared MIME, and detected file signature. Reject mismatch or ambiguous files.
- Consider re-encoding raster images with Pillow to strip metadata and normalize formats; if used, enforce pixel-count limits to prevent decompression bombs.
- Do not accept SVG or HTML uploads in the first release.
- PDFs must be treated as untrusted documents; do not execute embedded content.
- Generate opaque IDs using secure randomness. Do not use original filenames as storage paths.
- Use a storage root configured by the application and outside executable/static code directories.
- Resolve paths and enforce root containment before reading/deleting. Reject symlink targets and path traversal.
- Set safe download filenames and `Content-Disposition: attachment` for downloads.
- Serve previews with a validated MIME type and `X-Content-Type-Options: nosniff`; use a restrictive content security policy where compatible.
- Enforce ownership at the endpoint and repository layers.
- Clean temporary files on success, failure, timeout, and cancellation.
- Set retention/deletion rules. Session deletion must remove local attachments that are no longer referenced by any other message/session.

### 13.3 Provider file API lifecycle

- Store provider file IDs/URIs and expiration timestamps only as metadata.
- Re-check expiration before use; re-upload from local storage when possible.
- Delete remote files when the user deletes an attachment/session if the provider supports deletion.
- Remote cleanup is best-effort and must not leak secrets.
- Do not expose raw provider URIs in HTML or API responses.
- Show expired/unavailable attachment status in old messages, while retaining the local attachment according to the app’s retention policy.

## 14. Chat page UX specification

Use Kinetiqo’s existing layout, theme, icons, spacing, local assets, and responsive patterns. Avoid adding a new frontend framework. Keep JavaScript modular and compatible with the project’s lint/quality rules.

### 14.1 Desktop layout

- Left sidebar: “New chat” action, searchable/recent conversation list if feasible, title, last-updated order, rename, delete.
- Main panel: welcome state when no session is selected; conversation transcript; composer anchored at the bottom.
- Header: current conversation title, provider/model selector, and a menu for conversation actions.
- Assistant messages: readable Markdown, code blocks with copy action if practical, links with safe target handling, and attachment/source cards.
- User messages: plain text and attachment chips.
- Streaming state: animated but unobtrusive indicator, Stop button, and disabled duplicate-send behavior.
- Errors: inline, actionable, non-destructive; preserve the user’s prompt.
- Long messages: sensible line wrapping and horizontal scrolling for code blocks.

### 14.2 Mobile layout

- Sidebar becomes a drawer or collapsible panel.
- Composer and attachment controls remain usable on narrow screens.
- No horizontal page overflow.
- Keyboard opening must not hide the composer.
- All controls have visible focus states and adequate touch targets.

### 14.3 Composer behavior

- Enter sends; Shift+Enter inserts a newline. Provide a discoverable hint and avoid interfering with IME composition.
- Up arrow may restore the previous draft only when the composer is empty and not in the middle of IME composition. Keep prompt history in `sessionStorage` only if helpful; never persist secrets.
- Stop cancels the active request and preserves generated partial output as interrupted if it is retained.
- Retry creates a new generation for the failed turn without duplicating the user message.
- Send button is disabled for empty/whitespace-only prompts and while a turn is active, except Stop.
- File picker supports multiple allowed attachments and drag-and-drop only if keyboard-accessible equivalent controls exist.
- Show upload progress, file size, type, remove action, and clear validation errors before sending.
- Warn before navigating away during active generation if doing so would interrupt it.

### 14.4 Markdown safety

- Store raw Markdown, not HTML.
- Use the existing approved local Markdown library if available; otherwise add it through the repository’s vendor-library workflow.
- Sanitize rendered HTML with a maintained sanitizer and a restrictive allowlist. Markdown rendering alone is not sanitization.
- Disallow scripts, inline event handlers, dangerous URL schemes (`javascript:`, `data:` except tightly controlled image rendering), embedded iframes, and arbitrary HTML.
- Open external links safely with `rel="noopener noreferrer"` when using a new tab.
- Render code blocks without executing them.
- Do not render provider output with `innerHTML` unless it has been sanitized. Prefer safe DOM APIs for streamed text and status content.

### 14.5 Accessibility

- Use semantic landmarks and buttons.
- All actions must work by keyboard.
- Add accessible labels to icon-only controls.
- Keep focus predictable after new chat, rename, delete, upload, and error.
- Announce new streamed output and status changes without announcing every token to screen readers; use restrained `aria-live` behavior.
- Respect reduced-motion preference.
- Ensure light/dark theme contrast follows the rest of Kinetiqo.

### 14.6 Empty and error states

Provide clear states for:
- No provider key configured.
- Provider configured but model list unavailable.
- No conversations yet.
- Loading history.
- Upload in progress / upload rejected.
- Rate limit or quota exhausted.
- Invalid/revoked key.
- Network timeout/provider outage.
- Context limit reached.
- Attachment expired/unsupported.
- Tool unavailable or data not found.
- Generation stopped/interrupted.
- Session deleted or inaccessible.

Do not show raw stack traces, provider payloads, or sensitive tool output.

## 16. Security and privacy checklist

Implementation is not complete until every item is addressed and tested.

### Authentication and authorization
- Login required for all page/API endpoints.
- Session and attachment ownership is enforced in every repository query and endpoint.
- Client-supplied athlete IDs are ignored/rejected.
- Unowned resources return 404.
- CSRF protection on all mutating routes, including key management, uploads, cancellation, rename, delete, and message submission.

### Secrets and logs
- Provider keys encrypted at rest with authenticated encryption.
- No key in URLs, HTML, JS, browser storage, analytics, or logs.
- Redact authorization headers and provider errors.
- Never log full prompts, attachments, full tool payloads, or sensitive activity data by default.
- Encryption-key rotation and `SECRET_KEY` change consequences documented.

### Network and provider safety
- Fixed allowlisted provider endpoints; no client-controlled base URL (prevents SSRF).
- TLS verification remains enabled.
- Bounded connect/read/write timeouts.
- Bounded retries and no automatic retry after streamed output.
- Rate limits and concurrency limits per athlete.
- Provider error payloads sanitized before display.

### Uploads and downloads
- MIME/signature validation, size limits, safe names, opaque IDs, path containment, no symlink traversal.
- Attachment access requires owner checks.
- No direct static serving of private files.
- `nosniff` and safe `Content-Disposition`.
- Temporary and orphaned files are cleaned up.
- Treat PDFs, images, activity descriptions, and model output as untrusted content.

### Tool execution and prompt injection
- Chat has a separate read-only allowlist.
- No arbitrary SQL, shell, filesystem, sync, profile write, or Strava write tools.
- Tool arguments validated server-side.
- Tool output is treated as data, not instruction.
- Per-tool and per-turn time/output limits.
- Model cannot change the authenticated athlete identity.
- The system prompt is server-owned and not exposed as a UI feature.

### Frontend
- Sanitize Markdown output.
- Do not trust model-generated HTML or URLs.
- Escape conversation titles and filenames.
- No secrets in `localStorage` or `sessionStorage`.
- Use safe DOM operations for streaming.
- External links use safe attributes.

### Data lifecycle
- Explain that provider requests leave the self-hosted environment.
- Define local retention and deletion behavior.
- Delete local session data and attachment references on user deletion.
- Attempt remote file deletion when supported.
- Do not imply that deleting a Kinetiqo chat removes provider-side retention outside Kinetiqo’s control.

## 17. Performance and reliability

- Use asynchronous provider I/O in a way compatible with the current Flask/Gunicorn deployment. Verify the configured worker class and async behavior rather than assuming every Flask async route is a persistent async worker.
- Do not block the event loop with synchronous SDK calls. If a synchronous SDK is selected, use an appropriate executor or use async HTTP.
- Reuse clients only if lifecycle and per-athlete credentials remain isolated; never share a mutable client carrying one user’s key with another user.
- Do not hold DB transactions open during model calls.
- Paginate session lists and bound history loads.
- Index session lookup/order, message lookup/order, provider-key lookup, and attachment ownership lookup.
- Set server-side caps for response size, tool result size, total turn duration, and active requests.
- Handle upstream 429/5xx/timeouts and client disconnects cleanly.
- Keep the page usable if model listing fails; show cached known models only if safe and still valid, otherwise provide refresh/retry.
- Add useful structured logs with request/session IDs but no sensitive content.
- Do not add background queues unless required by measured runtime or deployment constraints.

## 18. Testing strategy and acceptance tests

Follow `AGENTS.md`: default tests are isolated, mocked, and must not make live network or database calls. Use the existing unittest/pytest patterns and patch at the correct import boundary.

### 18.1 Domain/service tests
- New session creation does not call a provider.
- Title derivation sanitizes whitespace/control characters and respects length limits.
- Message history is chronological and excludes inappropriate failed turns.
- One active generation per session is enforced.
- Provider/model selection is validated.
- Missing key and unsupported provider produce normalized errors.
- Provider errors map to stable application errors.
- Token usage and message status persist correctly.
- User message is persisted before upstream generation.
- Failed/interrupted generation does not masquerade as a complete response.

### 18.2 Provider tests (mocked)
- Key validation success, invalid credentials, rate limit, timeout, and provider outage.
- Model pagination and filtering.
- Text streaming with split/malformed/empty SSE chunks.
- Finish/safety/error handling.
- Usage extraction.
- Image and PDF request construction.
- Unsupported model capability is rejected before the upstream call.
- Cancellation closes the upstream stream.
- No key or secret appears in raised/displayed errors or logs.
- No real network requests in CI.

### 18.3 Encryption tests
- Encrypt/decrypt round trip.
- Different nonce per encryption.
- Tampered ciphertext fails authentication.
- Wrong key/version fails closed.
- Empty/missing encryption configuration is rejected.
- Legacy/rotation behavior is tested if supported.
- No plaintext fallback.

### 18.4 Repository/database tests
For PostgreSQL, MySQL/MariaDB, and Firebird repository implementations:
- Session create/list/get/rename/delete.
- Message insert/list/update with deterministic ordering.
- Provider-key upsert/get/delete.
- Attachment metadata CRUD and owner filtering.
- Transactions and rollback on failure.
- Large text content and attachment metadata are supported.
- Database-specific schema types/indexes are correct.
- Cross-athlete reads/writes are impossible through repository methods.
- Tests remain mocked unless the repository’s CI explicitly provides isolated integration databases.

### 18.5 Route/security tests
- Unauthenticated requests redirect or return the project’s standard unauthorized response.
- CSRF is required for mutating routes.
- Another athlete’s session/message/attachment/key cannot be accessed, renamed, deleted, or downloaded.
- Missing/invalid content type, malformed JSON, oversized prompt, too many files, and unsupported MIME are rejected.
- Client-supplied owner ID and arbitrary provider URI/path are ignored/rejected.
- Provider key never appears in API responses.
- Errors do not disclose provider internals.
- Download headers and filename sanitization are correct.
- Cancellation and duplicate submission behave correctly.

### 18.6 UI/static tests
- Chat page renders in light and dark themes.
- No key configured state and configured state work.
- Session list, create, rename, delete, and reload history work.
- Streaming text is appended safely and rendered Markdown is sanitized.
- Stop, retry, network disconnect, error, and upload states are handled.
- Keyboard-only interaction and mobile layout are reviewed.
- Vendor libraries are added through the existing development workflow; no ad-hoc CDN dependency.

### 18.7 Required manual verification
Before declaring the feature done:
1. Start the app against each supported DB schema path or validate schema generation with backend-specific tests.
2. Configure a Gemini key in Settings and verify save/validation/removal.
3. Start a chat, stream an answer, refresh, and confirm persistence.
4. Ask a question requiring a read-only Kinetiqo tool and verify the answer matches the tool result.
5. Upload a supported image and PDF; verify capability handling and user-facing errors for unsupported models.
6. Stop a long response and verify upstream cleanup/interrupted status.
7. Attempt cross-athlete session and attachment access using test users.
8. Verify deletion of a chat removes local attachment data and attempts remote cleanup.
9. Run the full documented test suite, lint/quality checks, and relevant frontend/vendor build steps.
10. Update documentation and report commands run, results, and known limitations.
