# Kinetiqo AI Chat — Implementation Specification

> **Status:** Ready for implementation (v3 — revised and hardened)
> **Scope:** First production-ready release of an authenticated, persistent, multimodal, data-grounded AI chat integrated into Kinetiqo.
> **Primary provider:** Google Gemini.
> **Architecture:** Provider-neutral core; only the Gemini adapter ships in the first release.
> **Database support:** PostgreSQL, MySQL/MariaDB, and Firebird.
> **Supersedes:** `docs/concepts/ai-concept.md` v2 on branch `mcp`. Replace that file with this document.
> **Required project instructions:** Read and follow `AGENTS.md`, `SKILLS.md`, `README.md`, `docs/MCP.md`, `docs/DATABASE.md`, and the relevant existing web, settings, authentication, database, and MCP implementation before changing code. The source code and tests are authoritative when documentation differs.

---

## 1. Purpose and product outcome

Add an AI Chat page to Kinetiqo so an authenticated athlete can ask natural-language questions about their training and receive useful, data-grounded answers without configuring a separate AI client or MCP connection. The chat behaves like a first-class product feature — comparable in ergonomics to ChatGPT, Claude, and Gemini web UIs — while reusing Kinetiqo's own data, analytics, authentication, and MCP tool layer.

The feature must reuse Kinetiqo's existing data, analytics, authentication, and MCP tool layer. It must not independently query Strava, duplicate analytics calculations in chat code, or become a second analytics engine.

Example questions:

- "Summarize my training over the last four weeks."
- "Compare this month with the same month last year."
- "What are my current fitness, fatigue, and form values?"
- "Which rides contributed most to my recent training load?"
- "Analyze my ride from yesterday. Did I pace the climbs well?" *(the model calls read-only Kinetiqo tools)*
- "Explain this activity chart." *(with an uploaded image)*
- "Review this training-plan PDF." *(where the selected provider/model supports PDF input)*

### 1.1 User-visible outcomes

A user can:

1. Configure and validate an AI provider API key in Settings.
2. Open `/chat`, start a conversation, select an available model, and send text.
3. See the answer stream incrementally, with clear loading, cancellation, error, and retry states.
4. Return later and see full conversation history, persisted in the database.
5. Create, rename, and delete conversations; conversations sort by most recent activity.
6. Attach supported images and PDFs, see attachment previews, and download attachments generated by the model.
7. Ask questions about their Kinetiqo training data through a tightly controlled, read-only tool interface, and see a "Data used" indicator when tools were consulted.
8. See which provider/model answered and, when available, input/output token usage.
9. Understand that prompts, selected data, and attachments are sent to the configured external AI provider, via an explicit disclosure.
10. Use the feature with any supported Kinetiqo database backend without database-specific behavior leaking into the service layer.
11. Stop a generation mid-stream and retry a failed turn without losing their prompt.
12. Use suggested starter prompts on an empty conversation to discover what the assistant can do.

### 1.2 Product principles

- **Athlete privacy:** every session, message, key, upload, and generated artifact is scoped to the authenticated athlete.
- **Data provenance:** answers about Kinetiqo data must be grounded in tool results, distinguish facts from interpretation, and never invent metrics.
- **Read-only tools:** chat tool calling must not trigger syncs, edit athlete settings, or write to Strava — regardless of MCP mutation flags.
- **Provider isolation:** provider-specific request/response formats stay inside provider adapters.
- **No hidden data transfer:** show a clear disclosure before the first external-provider request and when configuring a provider.
- **Progressive enhancement:** text-only chat works without attachment support; the app remains usable on desktop and mobile.
- **Familiar chat ergonomics:** adopt proven UX patterns from leading AI chats — streaming output, stop button, regenerate, copy-to-clipboard, markdown answers, model badge, usage indicator — adapted to Kinetiqo's Tailwind design system and dark mode.
- **No network in tests:** unit tests mock provider APIs, MCP execution, and database boundaries (per `AGENTS.md`).
- **Fit existing Kinetiqo:** use current authentication, CSRF, templates, Tailwind build, local vendor library process, repository abstraction, logging, and design conventions.

## 2. Scope and explicit non-goals

### 2.1 Included in first release

- Provider-neutral chat domain model and adapter interface.
- Gemini provider: key validation, model discovery, text streaming, supported image/PDF inputs, provider errors, and usage metadata where available.
- Encrypted per-athlete provider keys (AES-256-GCM envelope).
- Persistent conversations and messages for all three database backends.
- `/chat` UI: conversation list, model selector, markdown responses, streaming, retry, stop/cancel, keyboard accessibility, dark mode, suggested starter prompts, copy answer, regenerate.
- Upload and download of supported attachments, with server-side validation and safe storage.
- Read-only Kinetiqo data tools through the existing MCP/tool service layer, with a chat-specific allowlist.
- "Data used" provenance indicator per assistant turn.
- Unit tests, route tests, security tests, documentation, and deployment/configuration notes.

### 2.2 Not included in first release (deliberate non-goals)

- OpenAI, Anthropic, or Mistral provider implementations. The abstraction must make these addable without changing the chat service or persistence contract.
- Voice input/output.
- Shared or collaborative conversations; public chat links.
- Autonomous background agents or scheduled AI actions.
- Any chat-triggered Strava writes, profile writes, or synchronization.
- Vector databases, embeddings, or a separate RAG index.
- AI-generated images unless the chosen Gemini model and API response format explicitly support it and the implementation can safely persist and serve them. Text-only answers must not depend on image generation.
- Message editing / branching UI (planned v1.1 — the data model must not preclude it; see §5.2).
- Automatic conversation summarization unless implemented as an explicit, testable context-management feature. Never silently remove old history from the visible conversation.

### 4.2 Core request lifecycle

1. Browser sends an authenticated, CSRF-protected request.
2. Route validates shape, size, content type, and request limits.
3. Route resolves the session using `current_user.id`; failure to find a session owned by the user returns 404.
4. Service obtains the configured provider key from the database or documented environment override.
5. Service validates provider/model availability and attachment ownership/compatibility.
6. Service loads persisted history and constructs a bounded provider request. The system instruction is generated by the server, never supplied by the browser.
7. If tools are enabled, the model may request only allowlisted read-only tools. The server validates and executes each call, then sends structured tool results back to the provider. Tool-call/result rounds loop within the turn budget (§9.3).
8. Provider text deltas are sent as application-defined SSE events (§11.4).
9. On successful completion, the final assistant message, attachment metadata, provider/model, tool provenance, and token usage are persisted.
10. On failure or cancellation, the user message remains recoverable and the assistant turn is marked `failed`/`interrupted`; partial output must not be presented as a complete answer.
11. Every exit path closes the upstream stream and releases resources (`finally` blocks).

Do not hold a database transaction open while waiting for a model response.

## 5. Domain model and persistence contract

Use explicit domain types and validation. Database rows must not be passed directly into provider adapters or templates.

### 5.1 Conversation/session

Required fields:

- `session_id`: opaque UUID string generated server-side (`secrets`/`uuid4`).
- `athlete_id`: authenticated owner.
- `title`: non-null bounded string (max 120 chars); initially a safe placeholder such as "New chat".
- `provider`: provider key, e.g. `gemini`.
- `model_id`: selected model identifier.
- `created_at`, `updated_at`: UTC timestamps.
- `last_message_at`: for ordering; keep, since list order is "most recently active first".

Rules:

- Default list order: `last_message_at` descending (with `session_id` as a stable tiebreaker).
- Creating a conversation must not call an external provider.
- A session's provider/model can be changed for a new turn if the selected model is configured; record provider/model per message so historical turns remain interpretable.
- Rename is an explicit operation. Auto-title is derived from the first user message (truncated to the title limit) unless model-generated titling is deliberately added later.
- Titles must be length-limited and rendered as text, never HTML.
- Deleting a session deletes all its messages and owned attachment references, and attempts provider-side cleanup of remote file uploads where supported. Remote cleanup failure must not prevent local deletion (log it).

### 5.2 Messages

Each message must include:

- `message_id`: backend-compatible generated identifier or UUID.
- `session_id`, `athlete_id`.
- `role`: `user` or `assistant` for persisted visible messages. Tool calls/results are stored as structured internal parts (`tool_calls` JSON metadata on the assistant message), never confused with visible assistant prose.
- `content`: plain text / Markdown source; never pre-rendered HTML.
- `attachments`: nullable JSON descriptor list (§5.3); never raw file bytes.
- `tool_provenance`: nullable JSON — list of `{tool_name, args_summary, result_summary, duration_ms}` entries for the assistant turn; powers the "Data used" panel and debugging.
- `provider`, `model_id`: nullable for user messages; set for assistant responses.
- `status`: `complete`, `failed`, `interrupted`.
- `error_code`: nullable normalized error taxonomy code (§6.3) for failed turns.
- `input_tokens`, `output_tokens`: nullable integers if the provider reports them.
- `seq`: monotonically increasing per-session sequence number for deterministic ordering (preferred over timestamp ordering; adapt to existing DB conventions — e.g., PostgreSQL identity, MySQL auto-increment within session, or an explicit per-session counter for Firebird).
- `created_at`.

Persist user messages before making the provider request so a browser disconnect does not lose the prompt. Persist assistant output per the completion policy. If partial output is saved, it must be marked `interrupted` and clearly labeled in the UI.

Message history must load in deterministic chronological order (`seq`). The schema must not preclude future message editing/branching (v1.1): keep `content` mutable-by-update (no append-only constraint) and allow `regenerated_from` as a nullable future column or leave room for one.

### 5.3 Attachments

Persist only metadata in message JSON; keep bytes in the configured local artifact/upload store using opaque server-generated IDs.

Attachment descriptor fields:

- `attachment_id`
- `owner_athlete_id`
- `session_id` and/or `message_id` when associated
- `original_filename` (display-only, sanitized — no path components)
- `mime_type` (detected server-side from file signature, not the browser)
- `size_bytes`
- `sha256` (integrity/deduplication aid, not authorization)
- `storage_kind` (`local` or provider-managed reference)
- `storage_key` (opaque, server-generated key)
- `provider_file_id` / `provider_file_uri` only when needed
- `provider_file_expires_at` when applicable
- `created_at`
- optional `deleted_at`

Do not store user-controlled filesystem paths. Resolve attachment IDs to metadata in the database and then to a server-controlled storage location. Enforce ownership on upload association, viewing, download, deletion, and provider submission. Use the repository's path-boundary pattern (Sonar pythonsecurity:S8707): resolve storage keys within a dedicated attachment root, reject symlink targets, verify containment.

### 5.4 Provider keys

One key per athlete and provider:

- `key_id`
- `athlete_id`
- `provider`
- `api_key_enc`
- `key_version` (envelope version, enables rotation)
- `is_valid`
- `validated_at`
- `created_at`, `updated_at`

Add a unique constraint/index on `(athlete_id, provider)`. The database must never store provider API keys in plaintext. Do not return ciphertext or plaintext to the browser. The UI may show only a configured/unconfigured state and a masked suffix (last 4 characters) if the project's security policy explicitly permits it; safest default is not to display any key characters.

### 5.5 Schema sketches (portability notes — verify exact syntax against `schema.py`)

Illustrative PostgreSQL DDL; adapt naming/casing and type details to the project's existing schema conventions:

```sql
CREATE TABLE chat_sessions (
```

Portability requirements:

- **PostgreSQL:** identity columns and timezone-aware timestamps must match existing conventions.
- **MySQL/MariaDB:** auto-increment and index-length rules (index prefix lengths on `VARCHAR` columns for `UNIQUE (athlete_id, provider)` etc.); use `utf8mb4`; large text via `LONGTEXT`/`JSON` as conventions dictate.
- **Firebird:** identity support, identifier quoting, descending-index syntax, large text fields (`BLOB SUBTYPE TEXT`), booleans (`SMALLINT` per convention), and timestamp behavior must match the supported Firebird versions (3.0/4.0/5.0). Do not use short `VARCHAR` for large JSON — use BLOB.
- Do not assume `ON DELETE CASCADE` is available/consistent across all three backends. Explicit transactional deletion is acceptable and preferred.
- `UUID` handling differs per backend: store as `CHAR(36)`/`VARCHAR(36)` where native UUID types are unavailable (Firebird); generate server-side in Python with `uuid4()` for full portability if the project prefers that.
- All queries must be parameterized (`%s` for PostgreSQL/MySQL, `?` for Firebird). Table/column names come from static code, never request input.
- All writes spanning multiple rows must be transactional (session delete = messages + attachment metadata + storage files).
- Every query involving user data must constrain by owner (`athlete_id`) and relevant session/attachment ID.

### 5.6 Repository methods

Add the minimum coherent contract, with naming adapted to the existing repository style:

- Create/list/get/rename/delete sessions (all scoped by `athlete_id`).
- Update session `model_id`/`provider`/`last_message_at`.
- Insert user message; allocate `seq` atomically per session.
- Insert/update assistant message (status, final content, usage, provenance).
- List messages for owned session with pagination or a bounded history limit, in `seq` order.
- Insert/get/delete attachment metadata; associate attachment with a message/session.
- Get/upsert/delete provider key by athlete/provider; mark key validity and validation timestamp.
- Cleanup orphaned attachment metadata where appropriate (background or on-access).

Repository functions must return normalized domain records, not driver-specific row types. Add tests for every backend implementation using the project's mocking/testing conventions.

## 6. Provider-neutral contract

The core must not know Gemini request JSON, SSE payloads, or SDK types.

### 6.1 Shared types

```python
from dataclasses import dataclass
from typing import AsyncIterator, Literal, Protocol

Role = Literal["system", "user", "assistant", "tool"]

@dataclass(frozen=True)
class ChatAttachment:
    attachment_id: str
    mime_type: str
    filename: str
    size_bytes: int
    # Provider adapters receive validated content/reference objects,
    # never a client-supplied path or arbitrary URI.

@dataclass(frozen=True)
class ChatMessage:
    role: Role
    content: str
    attachments: tuple[ChatAttachment, ...] = ()

@dataclass(frozen=True)
class ToolCall:
    call_id: str
    name: str
    arguments: dict

@dataclass(frozen=True)
class ChatProviderModel:
    id: str
    display_name: str
    input_token_limit: int | None = None
    output_token_limit: int | None = None
    supports_vision: bool = False
    supported_mime_types: tuple[str, ...] = ()
    supports_tools: bool = False

@dataclass(frozen=True)
class Usage:
    input_tokens: int | None = None
    output_tokens: int | None = None

@dataclass(frozen=True)
class StreamEvent:
    type: Literal["text_delta", "tool_call", "usage", "completed"]
    text: str | None = None
    tool_call: ToolCall | None = None
    usage: Usage | None = None

class ChatProvider(Protocol):
    async def validate_key(self) -> None: ...
    async def list_models(self) -> list[ChatProviderModel]: ...
    def stream(
        self,
        *,
        model_id: str,
        system_instruction: str,
        history: list[ChatMessage],
        new_message: ChatMessage,
        tools: list[dict] | None = None,
        tool_results: list[dict] | None = None,   # supplied on continuation rounds
        max_output_tokens: int | None = None,
    ) -> AsyncIterator[StreamEvent]: ...
```

This is an illustrative contract, not a requirement to copy it verbatim. Choose one consistent interface and test it. In particular:

- Do not encode usage metadata in strings such as `__usage__:100:30`.
- Do not mix model output, errors, tool calls, and usage in a single untyped text stream.
- Do not expose SDK response objects outside the adapter.
- Provider-specific capabilities must be explicit; unsupported attachment types must fail before an API request with a clear message.
- Multi-round tool calling: the service must be able to resume the provider conversation with tool results — either via a stateful continuation API on the adapter or by replaying the full tool-call/result sequence as provider-native history. Pick one approach, implement it once, and test it; do not keep two production paths.

### 6.2 Provider registry

Use an explicit static registry, not dynamic imports from user input:

```python
PROVIDER_REGISTRY = {
    "gemini": GeminiChatProvider,
}
```

The provider key comes from validated server-side configuration/database records. Unknown providers return a controlled unsupported-provider error. Do not advertise unimplemented OpenAI/Anthropic/Mistral providers in the UI.

### 6.3 Error taxonomy

Normalize provider failures into application errors (`src/kinetiqo/chat/errors.py`):

- `ChatConfigurationError` — no key, invalid model, unsupported capability.
- `ChatAuthenticationError` — provider rejected key.
- `ChatRateLimitError` — throttled/quota exhausted.
- `ChatTimeoutError` — timeout.
- `ChatProviderUnavailableError` — upstream unavailable (5xx/network).
- `ChatProviderResponseError` — malformed or unexpected response.
- `ChatContextLimitError` — request exceeds context/input limits.
- `ChatAttachmentError` — invalid, expired, unsupported, or inaccessible attachment.
- `ChatCancelledError` — user stopped generation or client disconnected.
- `ChatSafetyBlockedError` — provider blocked the response (safety filters); surfaced distinctly so the user understands the answer was withheld, not failed.

Each error carries a stable `error_code` string persisted on failed messages and a safe, localized, user-facing message. Return safe, actionable messages to the browser. Log technical details without secrets, raw attachment contents, or full prompts. Never return provider stack traces or raw upstream error bodies.

## 7. Gemini provider implementation

Use the official Gemini API through the project-approved client library or `httpx` (already a dependency at 0.28.1), after verifying current API support and dependency compatibility. Prefer one approach for streaming and test it thoroughly; do not keep two production paths "just in case".

### 7.1 Authentication and key validation

- Send the key in the provider's supported authentication header (`x-goog-api-key`), never in a URL/query string.
- Use a bounded connection/read timeout (e.g., connect 10s / read 120s for streams; shorter for validation).
- Validate the key on save by making a lightweight authenticated request that confirms access (e.g., list models). Distinguish invalid credentials (401/403) from quota/network/server errors; do not mark a key invalid for a transient timeout.
- Never log the key, headers, full request body, or URL containing credentials.
- If validation fails, do not replace a previously working key unless the user explicitly confirms replacement or the route's behavior is clearly documented.
- Return a generic validation result to the browser; no secret material is returned.

### 7.2 Model discovery

- Fetch available models from the authenticated provider endpoint (`models.list`-equivalent).
- Filter by supported text-generation capability and any required capabilities (tool/function calling, vision/PDF input where relevant).
- Normalize IDs by removing provider resource prefixes (`models/gemini-...` → `gemini-...`) only if the actual chat endpoint expects the shortened identifier.
- Use provider-supplied model metadata when available; unknown metadata must be `None`/unknown rather than guessed.
- Handle pagination.
- Cache model results server-side with a TTL (initial target: 10 minutes) and invalidate when a key is changed or removed. A browser cache may be added for UX, but it must not be the source of truth or keyed by a truncated API-key hash.
- Do not assume model names, context sizes, output limits, or file-expiration periods are permanent. Treat them as provider metadata/configuration and verify the current API contract at implementation time.
- Return only models that are actually supported by the configured key and API endpoint.
- Mark in the selector when a model supports vision/PDF so users understand which attachments it accepts.

### 7.3 Streaming protocol

- Parse the provider's actual streaming protocol robustly, including partial network chunks and multi-line SSE events where applicable.
- Extract only supported text parts into `text_delta` events.
- Extract usage metadata if supplied (`usage` events; also final-usage on completion).
- Detect finish reason, blocked/safety responses, malformed events, and upstream errors; map them to the error taxonomy.
- Ignore empty/non-text parts safely; do not stringify arbitrary objects into the response.
- Always close response streams/clients in `finally`.
- Apply timeouts and handle cancellation/disconnection (client abort must propagate upstream promptly — close the provider stream when the SSE client disconnects).
- Do not retry a stream automatically after any output has been emitted, because this can duplicate or alter the answer. Retry only when the request is known not to have started, and only with bounded attempts (initial target: 1 retry, exponential backoff capped).

### 7.4 Multimodal requests

Build provider payloads from validated attachment descriptors and bytes resolved server-side.

- Supported first-release uploads: JPEG, PNG, WebP, and PDF, subject to actual provider/model support.
- GIF may be accepted only if it is intentionally supported and safely normalized; otherwise reject it. Do not claim a capability that is not tested.
- Validate actual file signatures/MIME (magic bytes), not only filename or browser-supplied MIME.
- Enforce limits before buffering or base64 encoding (initial targets: max 5 attachments per message, 10 MB per file, 20 MB per request; configurable).
- Use inline content only when within provider and application request-size limits (Gemini inline limit ~20 MB request; stay below it).
- For larger files, use the provider's File API only if the selected provider supports it; track remote IDs and expiration (`provider_file_expires_at`). Expired remote files must be re-uploaded from local storage if the original file still exists and the user sends it again.
- Do not rely on remote provider file storage as the only copy of a user attachment.
- A file URI must originate from a successful upload by this application; never accept arbitrary user-supplied provider URIs.
- Before sending a request, confirm the selected model supports every attachment MIME type; otherwise return a `ChatAttachmentError` before any API call.
- If upload succeeds remotely but local persistence fails, attempt remote cleanup.
- If the provider cannot return image outputs for the chosen model, treat image generation as unsupported rather than silently dropping the response part.

## 8. API key encryption and secret management

### 8.1 Encryption requirements

Use authenticated encryption (AES-256-GCM) from a maintained cryptographic library (prefer the `cryptography` package — add as a pinned runtime dependency per repository policy).

- Generate a fresh cryptographically secure nonce for every encryption operation; never reuse nonces.
- Derive a dedicated encryption key from the configured secret using HKDF-SHA256 and a fixed application-specific context string (e.g., `"kinetiqo-chat-key-encryption-v1"`).
- Store a versioned envelope, e.g. `v1:<base64(nonce || ciphertext_and_tag)>`, so future key-rotation/envelope changes are possible.
- Validate minimum secret configuration (≥ 32 bytes of entropy) at startup or when AI features are used.
- Never use `SECRET_KEY` directly as an AES key without a KDF.
- Never fall back to plaintext storage if encryption fails.
- Decryption failure must fail closed and produce an actionable operator message, not expose cryptographic details to the user.
- Use constant-time/standard library cryptographic primitives; do not implement cryptography manually.

### 8.2 Secret rotation and configuration

Because deriving the encryption key from Flask `SECRET_KEY` means changing it can make stored keys undecryptable:

- Document that consequence prominently.
- Prefer a dedicated environment setting `KINETIQO_CHAT_ENCRYPTION_KEY` consistent with the existing configuration model. If the project deliberately uses `SECRET_KEY`, specify the exact rotation behavior and test it.
- Support key versions: store `key_version`, accept a list of active versions (e.g., old + new during rotation), re-encrypt on next write, and implement an explicit rotation procedure documented in `docs/`.
- Do not expose encrypted values through settings APIs, HTML, logs, or exception messages.
- Environment-provided provider keys (`KINETIQO_CHAT_GEMINI_API_KEY`), if supported, must have explicit precedence and UI indication. A database key must not silently override an environment key or vice versa. Follow Kinetiqo's existing environment-vs-database settings policy and test it.
- Never add a provider key to `.env.example` with a real value.

### 8.3 Key settings UI

The AI settings section must:

- Explain that prompts, relevant Kinetiqo data, and attachments are sent to the selected provider.
- Show provider configured/unconfigured status and last successful validation time.
- Accept a new key via password input with autocomplete disabled where appropriate.
- Never populate the input with an existing key.
- Offer "Validate and save" and "Remove key".
- Distinguish invalid-key errors from quota/network errors.
- Require CSRF protection and authentication.
- Avoid leaking the key through query strings, analytics, browser storage, flash messages, or logs.
- Warn if a key is supplied by environment configuration and cannot be edited from the UI.

## 9. Kinetiqo MCP/tool integration

The chat must reuse the existing Kinetiqo data/tool layer (`src/kinetiqo/mcp/`). Do not implement a second SQL analytics layer for the AI.

### 9.1 First-release behavior

Implement **on-demand read-only tool calling** only if the existing tool layer can be invoked safely in-process with a well-defined contract. If not, ship a deterministic read-only context builder first and leave tool calling behind a feature flag (`KINETIQO_CHAT_TOOLS=0`) until the invocation contract is proven.

The final delivered first release must have a reliable way to answer data questions, not merely a generic chatbot with a hard-coded context snapshot.

### 9.2 Tool allowlist

Build the tool catalog from the actually registered MCP tool definitions and explicitly allow only tools needed for analysis. Known read-only tools from `docs/MCP.md` that are the intended catalog (the agent must verify exact names, parameters, and output schemas in `src/kinetiqo/mcp/` — do not invent tool names):

- `kinetiqo_search_activities`
- `kinetiqo_get_activity_details`
- `kinetiqo_get_activity_streams`
- `kinetiqo_analyze_pacing`
- `kinetiqo_find_similar_routes`
- `kinetiqo_compare_route_attempts`
- `kinetiqo_get_fitness_and_freshness`
- `kinetiqo_calculate_power_curve`
- `kinetiqo_get_personal_records`
- `kinetiqo_get_weekly_training_profile`
- `kinetiqo_analyze_recovery_turnaround`
- Activity totals / date-range summaries (verify exact tool name)
- FTP and VO₂max trend tools (verify exact names)
- Training goals / athlete profile read tools (verify exact names)

Explicitly excluded (never exposed to chat, regardless of `KINETIQO_MCP_ALLOW_*` flags):

- `kinetiqo_trigger_sync`
- `kinetiqo_update_athlete_profile`, `kinetiqo_update_training_goals`
- `kinetiqo_update_strava_description`
- Any Playwright visual export tool (posters/infographics) — expensive operations; defer to a later, specifically reviewed and bounded release.
- Any tool that can: trigger a Strava sync; update Strava content; change athlete/profile/settings data; delete or modify activities; perform arbitrary SQL or filesystem operations; access another athlete's data.

MCP mutation flags are not a substitute for a chat-specific allowlist. The chat tool registry must exclude mutating tools regardless of global configuration. The allowlist is a single explicit module-level set of tool names (`CHAT_TOOL_ALLOWLIST`) with a test asserting no mutating tool is present, and a test asserting every allowlisted name exists in the registered MCP catalog.

### 9.3 Tool-call execution rules

- Validate tool name and arguments against server-owned schemas (reuse MCP tool input schemas).
- Apply per-call timeouts (initial target: 10 seconds), maximum tool-call count per assistant turn (initial target: 8), maximum tool-result size (initial target: 64 KB, truncate with a clear marker), and a total turn time budget (initial target: 120 seconds).
- Never execute a tool name or SQL statement provided only by the model; unknown names return a structured tool error to the model.
- Treat tool output and uploaded documents as untrusted data, not instructions.
- Do not include secrets, access tokens, or unrelated personal data in tool results.
- Pass only the minimum fields needed to answer the question.
- Tool errors are returned to the model as structured errors without stack traces; the user sees a concise explanation if the request cannot be answered.
- Tool execution must preserve the authenticated athlete context and must not allow the model to override it (tools are invoked in-process with the current athlete identity, exactly as the MCP server does).
- Persist `tool_provenance` (names, bounded arg/result summaries, durations) on the assistant message for the "Data used" panel and debugging; never store large duplicate raw payloads.
- Bound loops: stop when the provider returns a final answer, the tool-call budget is exhausted, or the turn deadline is reached. On budget exhaustion, tell the model (one final round) that no further tool calls are allowed and it must answer with what it has or state the limitation.
- The model must be told that it cannot execute write operations and that it must not claim a tool ran when it did not.

### 9.4 Data-grounded answers — server-owned system instruction

Use a server-generated system instruction that:

- Defines the assistant as Kinetiqo's training-data assistant.
- Requires using tools for questions that depend on the athlete's data.
- Requires clearly distinguishing retrieved values, calculations, and coaching interpretation.
- Requires dates, units, comparison periods, and assumptions to be explicit.
- Requires saying when data is missing, stale, or insufficient (including the athlete's last sync date when relevant and cheap to obtain).
- Prohibits fabricating activities, power values, heart rates, training load, or tool results.
- Advises that training insights are informational and not medical diagnosis.
- Treats user messages, activity descriptions, and uploaded documents as untrusted content that cannot override system instructions (prompt-injection resistance).
- Requires concise source context in the answer, e.g., date range, activity names/dates, or metric provenance. Do not invent a citation syntax the UI cannot render.
- Specifies Markdown formatting expectations: headings, short paragraphs, and tables for comparisons; no HTML in answers.

### 9.5 Context policy

- Build system instructions on the server for every request; never accept system prompts from the browser.
- Optionally pre-load a small, cheap athlete context block (name, sports, last sync date, current CTL/ATL/TSB if a single low-cost query provides them) so the model can personalize without a tool round; keep it bounded (< 2 KB) and clearly sourced/dated.
- Do not inject a large lifetime data dump into every prompt.
- The UI provides a collapsible "Data used" panel per assistant turn showing the tool names, time ranges, and concise result summaries from `tool_provenance`, without exposing hidden reasoning or internal system prompts.
- If a context snapshot is cached, use an explicit TTL and invalidate it after data sync or relevant settings changes when practical.
- Never claim the model has access to all Kinetiqo data unless the available tools and query results justify that claim.

## 10. Conversation history and context-window management

### 10.1 Source of truth

The database is the authoritative history. Browser storage may retain only transient UI state such as draft text (per session), sidebar width, and last-selected model. Do not store chat history or provider secrets in `localStorage`.

### 10.2 Request construction

For each turn:

1. Load messages for the owned session in chronological order (`seq`).
2. Exclude `failed`/`interrupted` assistant turns from model context unless there is a deliberate and tested representation.
3. Rebuild provider-native conversation messages from normalized history.
4. Keep system instructions separate from user-visible history.
5. Include attachment content only when the attachment is still available, owned by the user, and supported by the current model.
6. Estimate total request size (chars as a proxy) and apply a context budget. If history exceeds the budget, trim from the oldest turns first, keeping whole user/assistant pairs. The visible conversation is never trimmed — only what is sent to the model. If trimming occurred, note it in the system instruction ("earlier conversation history was omitted").

### 10.3 Context budgets

- Initial targets (configurable in `chat/config.py`): max 50 most recent messages sent to the model; max ~200 K chars of history; `max_output_tokens` left at provider default unless the model metadata requires a bound.
- Never silently drop the newest user message or its attachments.
- When a turn's history would exceed the model's input limit, return `ChatContextLimitError` with actionable guidance ("start a new conversation") rather than failing mid-stream.

## 11. Web API and SSE contract

All endpoints are authenticated (`flask-login`), CSRF-protected on all non-GET methods (`flask-wtf` token or `X-CSRFToken` header), and scoped to `current_user.id`. Standard error envelope: `{"error": {"code": "<stable-code>", "message": "<safe-text>"}}` with appropriate HTTP status codes.

### 11.1 Endpoints

| Method | Path | Purpose |
|---|---|---|
| GET | `/chat` | Chat page (empty state or last session); redirects unauthenticated users per existing auth conventions. |
| GET | `/chat/<session_id>` | Chat page for a specific owned session (404 otherwise). |
| GET | `/api/chat/sessions` | List owned sessions (id, title, provider, model_id, updated_at, last_message_at), most recently active first. |
| POST | `/api/chat/sessions` | Create session `{provider, model_id?}` → `201` with session object. Never calls the provider. |
| PATCH | `/api/chat/sessions/<id>` | Rename (`{title}`) and/or change model (`{model_id}`). |
| DELETE | `/api/chat/sessions/<id>` | Delete session and owned message/attachment data (transactional). |
| GET | `/api/chat/sessions/<id>/messages` | Owned messages, chronological, paginated (`?before_seq=&limit=`), default limit 100. |
| POST | `/api/chat/sessions/<id>/messages` | Send a turn: `{content, attachments?: [attachment_id], model_id?}` → SSE stream response (or `202` + stream URL if the project prefers). Persists the user message first. |
| POST | `/api/chat/sessions/<id>/regenerate` | Re-run the last user turn: drops the previous assistant turn (keeps it as `interrupted`-style history or deletes per implementation choice — document and test the choice) and streams a new answer. |
| POST | `/api/chat/sessions/<id>/cancel` | Cancel the in-flight turn for that session (idempotent; `200` even if nothing was running). |
| GET | `/api/chat/models?provider=gemini` | Available models for the configured key (server cache, TTL). |
| POST | `/api/chat/attachments` | Multipart upload (image/PDF). Validates signature, size, count limits; returns descriptor without message association. |
| GET | `/api/chat/attachments/<id>` | Download owned attachment (correct `Content-Type`, `Content-Disposition`, `X-Content-Type-Options: nosniff`). |
| DELETE | `/api/chat/attachments/<id>` | Delete owned attachment (storage + metadata). |
| POST/DELETE | settings AI section (existing settings routes) | Validate/save/remove provider key (§8.3). |

Request limits: message content max 32 KB of text; enforce with explicit validation errors, not truncation.

### 11.2 Status codes

- `400` invalid shape/limits; `401` unauthenticated; `403` CSRF failure; `404` not owned/not found; `409` concurrent send to the same session (one in-flight turn per session per user — return a "still generating" error with the session state); `413` attachment too large; `422` unsupported MIME for the selected model; `429` provider rate limit (with retry-after when available); `502/504` upstream provider failures; `200` with SSE stream on success.

### 11.3 Concurrency and cancellation

- One active turn per session per user. A second send to the same session while a turn is in flight returns `409`.
- The server keeps a per-session cancel event; `/cancel` sets it, the streaming generator observes it, stops forwarding deltas, closes the upstream provider stream, and persists the assistant turn as `interrupted`.
- Client disconnect (SSE write failure) is treated as cancellation.
- In-flight turn state is in-memory only (single-process Flask/Gunicorn deployment assumption — verify; if multi-worker, document the limitation and use a database `active_turn` marker with a stale timestamp takeover).

### 11.4 SSE event protocol

Response headers: `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `X-Accel-Buffering: no` (if behind a proxy). Events are `event:` + `data:` lines with JSON payloads; a `data: [DONE]`-style terminator is not needed if `completed`/`error` events are authoritative.

| Event | Data payload | When |
|---|---|---|
| `session` | `{session_id}` | Stream start (confirms session state). |
| `user_message` | `{message_id, seq, created_at}` | The persisted user message (so the client can render it definitively). |
| `text_delta` | `{"text": "..."}` | Each provider text chunk. |
| `tool_call` | `{"name": "...", "status": "running"}` optional | Optional UX indicator that a tool is being consulted (name + running/done only; never args or raw results). |
| `usage` | `{"input_tokens": n, "output_tokens": n}` | When provider reports usage. |
| `completed` | `{message_id, seq, model_id, provider, usage, tool_provenance_count, attachments?}` | Final persist succeeded. |
| `error` | `{"code": "...", "message": "..."}` | Terminal failure; stream closes after. |

Rules: every event is a single JSON object on one `data:` line; the client must treat `error` and `completed` as mutually exclusive terminals; heartbeats (comment lines) every 15 s to keep proxies from timing out. Errors after any `text_delta` must carry `partial: true` and the assistant message is persisted as `interrupted` with the partial content.

## 12. Frontend specification

One page, one JS file (`static/js/chat.js`), server-rendered Jinja shell (`templates/chat.html`) extending `base.html`, progressive-enhancement style consistent with the rest of Kinetiqo (self-hosted vendor assets only; new client libraries must go through `development/vendor-libraries.yaml` and the downloader — never ad-hoc CDN tags; any remaining CDN reference must pin versions, include SRI, and update `license.html` per `AGENTS.md`).

### 12.1 Layout

- **Sidebar:** conversation list (title, relative last-activity time), "New chat" button, delete (with confirm modal), inline rename (double-click / edit affordance). Collapsible on mobile; width persisted in `localStorage` (UI state only).
- **Main area:** message thread; each message is a distinct element with a header row: role badge (You / assistant avatar), model badge (`gemini-2.x-…`) and usage chips on assistant turns (`▲ 1,234 · ▼ 567` style), and "Data used" collapsible on turns with tool provenance.
- **Composer:** textarea (auto-grow, Enter to send / Shift+Enter newline — verify platform behavior, provide explicit Send button too), attachment button with previews (thumbnail chips with name/size and remove), model selector dropdown (fetched from `/api/chat/models`), Stop button replacing Send while streaming, disabled state with reason when no key is configured (with a link to Settings).
- **Empty state:** suggested starter prompts (static, self-hosted, localized alongside existing strings): e.g., "Summarize my last four weeks of training", "How fresh am I right now?", "Compare this month to last year", "What are my best power efforts this season?" Clicking fills the composer.

### 12.2 States and behaviors

- **Streaming:** append `text_delta` chunks into a live element; auto-scroll to bottom unless the user scrolled up (then show a "jump to latest" affordance). Markdown is rendered live but conservatively (see §12.3).
- **Stop:** visible during streaming; calls `/cancel`; the partial turn is rendered with an explicit "Stopped" label.
- **Retry:** on `error` events, show a retry control that re-sends the same user content without re-persisting a duplicate user message (the route supports a `retry_of` hint or the client reuses the persisted user message).
- **Regenerate:** on the last assistant turn, re-runs the turn (§11.1).
- **Copy:** per-message copy button using the persisted Markdown source (`navigator.clipboard`, fallback to exec command).
- **Errors:** inline, non-blocking banners with the safe message and error code; the prompt is preserved in the composer.
- **Disclosure:** before the first send ever (per athlete), show a one-time modal: "Your prompts, relevant Kinetiqo data, and attachments are sent to Google (Gemini) using your API key. [Acknowledge]". Persist acknowledgment server-side (a per-athlete flag in settings or the provider-key row) so it survives devices; do not rely on `localStorage` alone.
- **Key unconfigured:** empty state shows a setup card linking to Settings with concise steps.

### 12.3 Markdown rendering policy

- Assistant and user content is stored and transported as Markdown; rendering happens client-side.
- Use a self-hosted Markdown renderer added via the vendor pipeline (e.g., `marked` + `DOMPurify`, or `markdown-it` + sanitizer), pinned with SRI if any CDN is used, or vendored locally per the self-hosting rule.
- Sanitize all rendered HTML; allow only a conservative tag allowlist (headings, lists, tables, code, emphasis, links). Links get `rel="noopener noreferrer"` and open per the project's external-link policy.
- Never `innerHTML` with unsanitized model output (Sonar Web:S5725); construct DOM via the sanitizer's API; `textContent` for any raw insertions.
- Code blocks get a language label when the model provides one; no copy button required in v1.
- Do not render model-emitted raw HTML — strip it.

### 12.4 Accessibility, keyboard, and quality rules

- Every control has an accessible label (`<label for>` or `aria-label`) per Sonar Web:S6853, including the sidebar toggle, attachment chips, and model selector.
- Full keyboard support: Send, Stop, Escape to cancel streaming, arrows to move between conversations (nice-to-have), focus management when switching sessions; `aria-live="polite"` region for streaming answer summaries (append at sentence boundaries, not every delta, to avoid screen-reader flooding).
- JS standards per `SKILLS.md`: `Number.parseInt(x, 10)`, `Number.parseFloat`, `Number.isNaN`, `Number.isFinite`; no duplicate object keys; no global functions (Sonar S7773/S1534).
- Dark mode via the existing Tailwind dark-theme tokens; test both themes.
- Mobile: composer fixed, sidebar overlays, touch targets ≥ 44 px.
- `|tojson` for any server-injected JSON into `<script>` blocks; never `|safe` for model or user content.
- All text strings follow the project's existing localization/string conventions.
